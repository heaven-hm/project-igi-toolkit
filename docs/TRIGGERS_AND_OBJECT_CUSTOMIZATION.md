# Mission Triggers & Extended Object Customization

This vertical slice adds two related capabilities to the ToolKit:

1. **Configurable mission success/failure triggers** (issue #15).
2. **Extended in-game object customization** by *parameter name* rather than
   hard-coded argument offsets (issue #12, "more than customizing in game
   objects").

Both are exposed in the editor as a new **"Triggers & Objects"** tab.

## Mission success / failure triggers

The game evaluates a `Task_New(10, "LevelFlow", ...)` task. Its `Complete` and
`Failed` arguments are QScript boolean expressions over other task states,
for example:

```text
Task_New(10, "LevelFlow", "", 0, 0, 0, 0, 0, 0, 0,
    "CutScene_1204.isFinished", "StatusMessage_1391.isSendt", FALSE, 0);
```

The Trigger Toolkit lets you:

- pick a **preset** grounded in the retail `objects.qsc` shipped with the
  repo, or build a custom expression;
- add/remove trigger leaves with **AND** for success and **OR** for failure;
- negate a trigger (`!` / parentheses);
- enable the in-game timer and set the maximum play time;
- optionally regenerate the aggregate failure `StatusMessage` so LevelFlow
  listens to `StatusMessage_<id>.isSendt`, matching retail convention.

Presets (issue #15):

| Preset | Success | Failure |
| --- | --- | --- |
| Jones steals the truck and escapes the base | `EditVariable_199.nValue == 1 && CutScene_1204.isFinished` | `HumanPlayer_0.isDead \|\| Car_1099.isExploded \|\| HumanSoldier_4023.isDead` |
| Enemies kill Harrison's man | existing success expression | `HumanSoldier_<harrison>.isDead` |
| Jones destroys Priboi's limo | `Car_<limo>.isExploded` | existing failure expression |

Task ids are resolved from the loaded `objects.qsc` (by task note or by AI
model id such as `022_01_1` for HARRISON) with level-one fallbacks, so the same
code works for custom missions.

Expressions are parsed into a small AST. `A && (B || C)` survives a load/save
cycle — unlike a flat "split on `&&` and `||`" approach, the operator order and
parentheses are preserved.

## Extended object customization

`Task_DeclareParameters(...)` entries in `objects.qsc` are now parsed by name.
The object customizer shows every declared property of the selected task with
its current value, and applies edits to individual argument spans:

- property names instead of magic indices (`Model`, `Open door`, `Can fire`,
  `Play sound`, `Explosion sound`, etc.);
- type-aware validation (bool, numeric, RGB/multi-value widths);
- values round-trip byte-for-byte — nested `Task_New` calls and newlines inside
  a task (e.g. `Car 1099` contains `AnimTask` and `AIGraph`) are untouched;
- editing is idempotent and rejects unknown properties.

This covers the object/sound-related part of issue #12. The other items raised
there (home-screen/menu editing, i18n language packs, level intro video) are
already served by the QVM Editor and community language mods as noted by the
maintainer on that issue; they are not part of this slice.

## Verification

```sh
# core logic + generated evidence (uses the installed .NET SDK)
dotnet run --project tests/Core.Tests/Core.Tests.csproj -c Release

# full editor build (needs Mono msbuild and Newtonsoft.Json from IGIEditor/newtonsoft.zip)
msbuild IGIEditor/IGIEditor.csproj /t:Rebuild /p:Configuration=Release

# GUI/CUA proof (headless Chrome + DevTools, no npm packages)
node tools/gui-proof/drive.mjs
```

Evidence written by these commands:

- `evidence/core-tests.txt` — assertion-by-assertion results.
- `evidence/gui-proof.png`, `evidence/gui-proof-interaction.png` — rendered UI
  preview before/after interaction.
- `evidence/gui-proof-interaction.txt` — CDP click results and verdict.

### Scope of the evidence

The WinForms editor **builds** on this host (Mono `msbuild` succeeded), but
Mono's 64-bit macOS WinForms backend cannot display a form
(`HIViewPlaceInSuperviewAt` / Carbon 64-bit limitation). The GUI proof is
therefore an HTML preview harness populated with QScript generated by the real
C# core, driven through Chrome DevTools. It is **not** a claim of live in-game
success: compiling to QVM and validating behaviour inside Project I.G.I still
requires the Windows/Wine game workflow.
